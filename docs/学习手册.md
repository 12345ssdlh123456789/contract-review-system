## 一、先看清楚：这个项目和企业 Demo 的差别在哪

大部分「AI 应用 Demo」长这样：一个输入框 → 调模型 → 显示结果。半小时能写完。

企业级要多出来的东西，**几乎全在两头**：

| 环节 | Demo | 企业级 | 为什么 |
|---|---|---|---|
| 开工前 | 直接写代码 | 先造评测集（带标准答案的样本） | 没有评测集，你永远不知道改动是变好还是变坏 |
| 权限 | 前端把按钮藏起来 | 权限在 SQL 的 WHERE 里 | 前端藏按钮 = 装饰，抓包就能绕过 |
| 模型挂了 | 报错弹窗 | 降级到规则引擎，界面标"降级模式" | 业务不能因为模型 503 就停摆 |
| 改 prompt | 直接改代码 | 存数据库、带版本号、可一键回滚 | 改三个字可能让召回率掉 30 个点 |
| 成本 | 不知道花了多少 | 每次调用记 token/耗时/成本，有护栏 | 一个死循环能烧掉一个月预算 |
| 日志 | print | append-only 审计表，带操作人/时间/IP | 合规审查就看这个 |
| 质量 | 感觉还行 | 每次改动跑分，看召回率/误报率变化 | "感觉"不是证据 |

一句话：**企业级 AI 是在用概率性组件，搭一个需要确定性 SLA 的系统。**
多出来的工作量，就是用来吸收那个"概率性"的。

### 一次审查请求的完整链路

这是全项目最核心的一条线，务必看懂：

```
1. 前端 POST /api/contracts/{id}/review  （带 Bearer token）
2. security.get_current_user 解 JWT → 得到 User 对象
3. contracts._get_visible_contract   ← SQL 层就过滤掉不该看的合同
4. contracts._visible_clauses        ← 条款级再过滤一次
      财务打开时，liability / termination 条款在这里就被剔除了
5. review_service.review_contract
     a. get_active_prompt(db)        取当前生效的 prompt 版本
     b. render_clauses_text(可见条款) 渲染成带编号的文本
     c. 成本护栏：估算 token，超限直接抛错，不发请求
     d. llm.chat()                   调模型（带 2 次指数退避重试）
     e. 失败？→ rule_based_review()  降级到正则规则引擎
     f. llm.extract_json()           从回复里抠 JSON（容错 markdown 包裹）
     g. normalize_findings()         清洗：丢弃编造的条款号、映射中文类别
6. save_review  落库（含 token/耗时/成本/降级标记）
7. write_audit  写一条审计（谁、什么时候、审了哪份、成功否）
8. 返回 ReviewOut，前端渲染
```

**注意第 4 步的位置** —— 权限过滤发生在调模型**之前**。
财务审查时，违约责任条款根本不会进入 prompt，模型没有机会泄漏它。
这比在 prompt 里写「别提违约责任」可靠一万倍。

## 三、第一步：先定评测集，再写代码

**这是全项目最值钱的部分，也是 90% 的项目会跳过的一步。**

### 为什么必须第一步做

假设你先写完代码，然后有人问「你这个准确率多少」，你只能回答"感觉挺准的"。
然后你想优化 prompt，改完更没底了 —— 因为你不知道是变好了还是变坏了。

有了评测集，你就有了一把尺子：
- 改 prompt 前跑一次：召回率 88.9%，误报率 31.1%
- 改 prompt 后跑一次：召回率 83.3%，误报率 20.4%
- 结论：**牺牲了 5.6 个点的召回，换回 10.7 个点的精确度**，F1 从 58.7% 涨到 64.5%

这个对比，比任何架构图都能说服人。

### 评测集怎么造（`backend/app/eval_dataset.py`）

20 份合成合同，覆盖 4 种类型，每类 5 份：

| 类型 | 用例 | 特点 |
|---|---|---|
| 采购 PUR | 001–005 | 账期风险、责任不对等、多重风险、正常样例 |
| 服务 SVC | 001–005 | 典型风险、自动续约陷阱、付款模糊、云服务数据风险 |
| 租赁 LSE | 001–005 | 押金与解除、维修责任不清、无限保密+异地管辖 |
| 保密 NDA | 001–005 | 单向义务、竞业限制缺失、权利归属风险、永久保密 |

**关键设计：故意混入「正常样例」**。
PUR-004、SVC-004、LSE-004、NDA-003 这 4 份是**没有埋雷的干净合同**。
它们的作用是测**误报率** —— 如果模型在干净合同上也能报出 3 条问题，
说明它在"过度联想"，上线后法务会被大量噪音淹没。

一份用例长这样（结构简化）：

```python
EvalCaseData(
    case_id="PUR-001",
    title="办公设备采购合同（高风险样例）",
    contract_type="采购",
    content="""第一条 合同标的
甲方向乙方采购...（正常条款）

第六条 违约责任
乙方逾期交付的，应按日支付违约金；甲方逾期付款的，
乙方有权要求甲方承担全部连带赔偿责任，且无金额上限。
...
""",
    risks=[
        PlantedRisk(clause_no=6, category="liability",
                    keywords=["连带", "上限", "不对等"], level="high"),
        PlantedRisk(clause_no=7, category="termination", ...),
        PlantedRisk(clause_no=8, category="dispute", ...),
    ],
    normal_clause_count=7,   # 用来算误报率的分母
)
```

### 评分逻辑（`eval_runner.py:score_case`）

```python
for risk in data.risks:              # 遍历每个埋好的雷
    for f in findings:               # 遍历模型报的每一条
        if f["clause_no"] != risk.clause_no:  continue   # 条款号必须对上
        if any(kw in f["issue"]+f["suggestion"] for kw in risk.keywords):
            hit = True               # 关键词命中 → 算抓到
        elif f["category"] == risk.category:
            hit = True               # 或类别对上 → 也算抓到
```

三个指标：

- **召回率 recall** = 抓到的雷 / 埋的雷总数（36 个雷）
  → 回答"漏没漏"，这是**第一优先级**
- **误报率 fpr** = 误报条数 / 正常条款总数（132 条）
  → 回答"烦不烦"
- **F1** = 两者的调和平均
  → 综合分

**企业取舍非常明确：宁可误报，不可漏报。**
漏一条无限连带责任，可能赔掉一年利润；误报一条，法务多看一眼而已。
所以召回率优先，误报用「低置信度不展示」来控制。

## 四、第二步：数据模型 —— 权限必须能在 SQL 层表达

看 `backend/app/models.py`。三个设计要点：

### 1. 用户带 `dept_id`，合同也带 `dept_id`

```python
class User(Base):
    role: Mapped[str]        # submitter / reviewer / finance / admin
    dept_id: Mapped[int | None]

class Contract(Base):
    submitter_id: Mapped[int]
    dept_id: Mapped[int | None]
```

这样查询时可以直接：

```python
stmt = stmt.where(or_(Contract.dept_id == user.dept_id,
                      Contract.submitter_id == user.id))
```

**数据库根本不会返回越权行**，内存里也就不存在泄漏的可能。
对比一下错误做法：`SELECT *` 全查出来，然后在 Python 里 `if user.role != 'admin': 过滤掉`。
后者一旦有人写了新的接口忘了过滤，就漏了。

### 2. 合同按「条款块」存储，不是整篇存

```python
class Clause(Base):
    contract_id: Mapped[int]
    order_no: Mapped[int]     # 第几条
    heading: Mapped[str]      # "第六条 违约责任"
    content: Mapped[str]
    category: Mapped[str]     # payment / liability / termination / ...
    visibility: Mapped[str]   # "all" 或 "submitter,reviewer,admin"
```

**为什么必须拆到块级**：财务只能看付款条款，看不到违约责任。
如果整篇存一个 `raw_text`，你就只能在 prompt 里说「别提违约责任」——
这是自欺欺人，模型完全可能顺口提一句。

拆成块之后，`_visible_clauses()` 在喂给模型之前就把不可见的块剔除了。
模型连"知道"的机会都没有。

`visibility` 的默认值在 `parser.py:CATEGORY_VISIBILITY`：

```python
CATEGORY_VISIBILITY = {
    "payment": "all",                          # 付款条款所有人可见
    "liability": "submitter,reviewer,admin",   # 违约责任财务看不到
    "termination": "submitter,reviewer,admin",
    "confidentiality": "submitter,reviewer,admin",
    "dispute": "submitter,reviewer,admin",
    "delivery": "all",
    "ip": "submitter,reviewer,admin",
    "other": "all",
}
```

### 3. `Review` 表保留每次调用的完整上下文

```python
class Review(Base):
    prompt_version_id: Mapped[int | None]   # 这版意见是哪版 prompt 出的
    model_name: Mapped[str]                 # 哪个模型
    findings: Mapped[list]                  # JSON 数组
    degraded: Mapped[bool]                  # 是否降级
    prompt_tokens / completion_tokens / total_tokens
    latency_ms / cost_cny                   # 耗时和成本
    reviewer_action: Mapped[str]            # accepted / edited / rejected
    reviewer_edits: Mapped[dict | None]     # 法务改了什么
```

要能回答这个问题：**"这条意见是哪版 prompt、哪个模型、哪次调用产生的？"**
答不上来，就没法做归因，也就没法迭代。

`reviewer_edits` 是数据飞轮的入口：法务改过的地方，自动进待标注队列。

### 4. 审计表没有 update / delete 方法

```python
class AuditLog(Base):
    user_id / username / action / target_type / target_id
    detail / ip_address / user_agent / success / created_at
```

代码里只有 `write_audit()` 一个写入函数，**没有任何修改或删除的入口**。
append-only 是审计可信的前提 —— 任何"能改审计日志"的设计，在合规审查里直接不合格。

## 五、第三步：认证与三层权限

`backend/app/security.py` 开头有一段注释，值得抄下来：

> 三个层次，缺一不可：
> 1. **认证**（Authentication）：你是谁 —— JWT 令牌
> 2. **授权**（Authorization）：你能做什么 —— 角色检查
> 3. **数据隔离**（Data Isolation）：你能看到哪些行 —— SQL 层过滤
>
> 初学者最容易只做第 1 层，然后在界面上把按钮藏起来当权限。
> **那不是权限，那是装饰。**

### 密码：为什么用 bcrypt 不用 SHA256

```python
def hash_password(password: str) -> str:
    return bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12)).decode()
```

SHA256 太快 —— GPU 一秒能试几十亿次。
bcrypt 故意慢（12 轮，约 0.25 秒/次），暴力破解成本高几个数量级。
而且 bcrypt 自动把盐存在哈希串里，不用自己管理。

### JWT：什么能放，什么不能放

```python
payload = {
    "sub": str(user.id),
    "username": user.username,
    "role": user.role,
    "iat": now,
    "exp": now + timedelta(minutes=480),   # 8 小时
}
```

**不要把密码、手机号放进 payload**。JWT 只是签名，不是加密 ——
任何人都能 base64 解开看内容。签名只保证"没被篡改"，不保证"看不见"。

### 角色门禁：装饰器式

```python
def require_roles(*roles: str):
    def _checker(user: CurrentUser) -> User:
        if user.role not in roles:
            raise HTTPException(403, detail=f"当前角色无权执行此操作")
        return user
    return _checker

# 用法
@router.get("/audit")
def list_audit(user: Annotated[CurrentUser, Depends(require_roles("admin"))]):
    ...
```

这是"能做什么"的检查；"能看哪些行"还要在查询里再过滤一次。两者不能互相替代。

### 三个层次怎么落到代码里

| 层次 | 实现位置 | 例子 |
|---|---|---|
| 认证 | `get_current_user()` | 没带 token → 401 未登录 |
| 授权 | `require_roles("reviewer","admin")` | 财务调审查接口 → 403 无权 |
| 数据隔离 | `contract_visibility_filter()` + `clause_visible()` | 财务看合同 → SQL 只返回 payment/delivery 条款 |

**实测验证**（三个角色打开同一份 7 条条款的合同）：

```
finance     clause_total=7  返回 clauses=2  可见=[payment, delivery]
submitter   clause_total=8  返回 clauses=8  （自己部门的合同）
reviewer    clause_total=7  返回 clauses=7  （全部可见）
```

财务确实只拿到 2 条，另外 5 条**后端根本没返回**，不是前端藏起来的。

## 六、第四步：合同解析 —— 最容易被低估的工作量

`backend/app/parser.py`

### 为什么这块最坑

审查意见要"定位到第 6 条"。如果解析出来的条款是错位的，
模型说得再对，指向的也是错的条款 —— 整个结果就是废的。

真实合同里：PDF 有表格、DOCX 有页眉页脚、扫描件没文字层、
条款编号有「第六条」「六、」「（六）」「6.」「6.1」五种写法混用。

### 条款切分：四种正则覆盖

```python
CLAUSE_PATTERNS = [
    re.compile(r"^\s*(第[一二三四五六七八九十百零〇\d]+条)\s*[:：、.]?\s*(.*)$"),
    re.compile(r"^\s*([一二三四五六七八九十]+)[、.．]\s*(.*)$"),
    re.compile(r"^\s*[（(]([一二三四五六七八九十]+)[)）]\s*(.*)$"),
    re.compile(r"^\s*(\d+(?:\.\d+){0,3})[、.．]?\s+(.*)$"),
]
```

兜底：一个标题都没识别出来 → 按空行切段落，至少不会整份当一个块。

### 条款分类：关键词打分

```python
def classify_clause(heading, content) -> str:
    blob = f"{heading} {content}"
    scores = {cat: sum(1 for kw in kws if kw in blob)
              for cat, kws in CATEGORY_KEYWORDS.items()}
    return max(scores.items(), key=lambda kv: kv[1])[0] if scores else "other"
```

这套关键词表一物两用：
1. 决定条款的 `visibility`（谁能看）
2. **模型挂了之后，规则引擎靠它兜底**

### 质量自检：宁可拒单

```python
def check_quality(text, clauses) -> dict:
    issues = []
    if char_count < 200:
        issues.append("正文太短，可能解析失败或文件为空")
    if heading_hits == 0 and len(clauses) > 0:
        issues.append("未识别到任何「第X条」标题，条款结构可能错位")
    if replacement_chars / char_count > 0.01:
        issues.append("乱码字符占比过高，可能是编码问题")
    return {"ok": len(issues) == 0, "issues": issues, ...}
```

`ok=False` 时**直接拒单**，不进入审查流程。

**为什么宁可拒单**：一份错位的审查结果比没有结果更危险 ——
法务会以为 AI 检查过了，实际检查的是别的东西。

## 七、第五步：LLM 调用与降级链

`backend/app/llm.py` + `review_service.py`

### 超时要分级

```python
LLM_CONNECT_TIMEOUT = 10    # 连接超时短
LLM_READ_TIMEOUT = 120      # 读取超时长
```

LLM 首 token 慢是常态（实测 glm-4-flashx 单份合同 5–9 秒），
用一个 30 秒的全局超时糊过去，会把正常请求也掐掉。

### 重试只重试「可重试」的

```python
except APITimeoutError:      → 重试
except APIConnectionError:   → 重试
except APIStatusError as exc:
    if 400 <= code < 500 and code != 429:
        break                # 401/403/400 重试一万次也没用，直接退出
```

退避策略：`time.sleep(2 ** attempt)` → 1s, 2s。
`max_retries=0` 传给 SDK —— **不让 SDK 偷偷重试**，重试策略必须自己控制，
否则你以为是 1 次调用，实际打了 4 次，成本算不准。

### 降级链：模型挂了不能整个功能不可用

`review_service.py` 里有三种触发降级的场景：

| 场景 | 处理 |
|---|---|
| `llm.chat()` 返回 `ok=False`（超时/连接失败/5xx） | → `rule_based_review()` |
| 返回了内容，但 `extract_json()` 解析不出 JSON | → `rule_based_review()` |
| token 预估超过单份上限 | → **直接抛错拒单**（不发请求，不降级） |

规则引擎有 8 条硬规则：

```python
RULE_RULES = [
    {"name": "账期过长", "pattern": r"(?:账期|付款期限)[^。；\n]{0,20}?(\d{2,3})\s*(?:个)?(?:日|天)",
     "check": lambda m: int(m.group(1)) > 90, ...},
    {"name": "预付比例过高", "check": lambda m: int(m.group(1)) > 50, ...},
    {"name": "单方解除权", ...},
    {"name": "连带责任无上限", ...},
    {"name": "异地管辖", ...},
    {"name": "无限保密期限", ...},
    {"name": "自动续约无退出", ...},
    {"name": "违约金比例过高", "check": lambda m: int(m.group(1)) > 30, ...},
]
```

准确率明显不如 LLM（实测召回率 25% vs 88.9%），但：
- 永远不会超时
- 永远不会花钱
- 至少能抓到最硬的几类问题

**关键：降级必须让用户知道。**
`ReviewOutcome.degraded=True` 会一路传到前端，界面上打黄色横幅：

> ⚠ 模型服务当前不可用，已自动切换到规则引擎审查。
> 规则引擎识别出 2 处问题，准确度低于 AI 审查，建议人工复核全部条款。

偷偷降级、界面看起来一切正常 —— 这是最糟糕的设计。

## 八、第六步：结果校验 —— 模型会撒谎

`review_service.py:normalize_findings()`

### 模型最常犯的三种错

1. **编造不存在的条款号**：合同只有 12 条，它说"第 15 条有问题"
2. **level 写成中文**：`"高"` / `"中"` 而不是 `"high"` / `"medium"`
3. **类别写成中文**：`"违约责任"` 而不是 `"liability"`

### 处理策略

```python
valid_nos = {c.order_no for c in clauses}

for item in raw:
    no = int(item.get("clause_no", 0))
    if no not in valid_nos:
        continue                    # 编造的条款号 → 直接丢弃

    level = level_map.get(level, level)   # 中文 → 英文
    if level not in VALID_LEVELS:
        level = "medium"

    if category in CATEGORY_ALIASES:      # 中文类别 → 英文枚举
        category = CATEGORY_ALIASES[category]
    if category not in VALID_CATEGORIES:
        # 类别不认识时，用条款文本自己重新判断一次，比直接归 other 准
        matched = next((c for c in clauses if c.order_no == no), None)
        category = classify_clause(matched.heading, matched.content) if matched else "other"
```

`CATEGORY_ALIASES` 有 30 多个映射：

```python
"付款": "payment", "支付": "payment", "价款": "payment",
"违约": "liability", "责任": "liability", "赔偿责任": "liability",
"解除": "termination", "终止": "termination",
...
```

**不做这一步会怎样**：所有中文类别都会掉进 `other`，
评测时 `category` 匹配全部失效，召回率会莫名其妙掉一大截 ——
你会以为是 prompt 的问题，实际是校验层的问题。这个坑真实踩过。

**原则：宁可少一条，不要错一条。**
坏数据直接丢弃，不猜、不补。

## 九、第七步：Prompt 版本化与一键回滚

`backend/app/prompts.py`

### 为什么要版本化

你今天改了三个字，线上召回率从 91% 掉到 62%。
如果没有版本号，你连"改之前是什么样"都找不回来。

### 存数据库，不存代码

```python
class PromptVersion(Base):
    name: Mapped[str]              # "contract_review"
    version: Mapped[int]           # 1, 2, 3...
    system_prompt: Mapped[str]
    user_template: Mapped[str]
    note: Mapped[str]              # 这版改了什么
    is_active: Mapped[bool]        # 当前生效的是哪版
    created_by: Mapped[int | None]
    __table_args__ = (UniqueConstraint("name", "version"),)
```

**每次修改新增一行，不覆盖旧行。**

切换版本就是：

```python
db.execute(update(PromptVersion).values(is_active=False))
db.execute(update(PromptVersion).where(id == target).values(is_active=True))
```

五分钟内能回到昨天。

### v1 vs v2 的真实差别

| | v1 初版 | v2 强化版 |
|---|---|---|
| system_prompt 长度 | 180 字 | 1003 字 |
| 审查维度清单 | 无 | 8 个维度逐条列举 |
| 输出格式约束 | 最简 JSON | 严格 JSON + 完整示例 |
| 条款定位要求 | 无 | "clause_no 必须准确，不要编造" |
| 置信度 | 无 | "0~1，低于 0.5 的不要输出" |
| level 判定标准 | 无 | "high = 重大经济损失；medium = 不利但可控；low = 表述瑕疵" |
| 负向约束 | 无 | "只报告确实存在于合同文本中的问题" |

v2 里最关键的三段（很多人写 prompt 会漏掉）：

```
【判定标准】
- level: high = 可能导致重大经济损失或丧失关键权利；medium = 存在不利但可控；low = 表述瑕疵
- confidence: 0~1 之间的小数，你对这条判断的把握程度。低于 0.5 的不要输出
- clause_no: 对应输入的条款序号（整数），必须准确，不要编造不存在的条款号

【重要】
- 只报告确实存在于合同文本中的问题。不要凭空推测合同里没写的内容
- 不要报告"建议补充完善"这类泛泛而谈的意见，除非该条款确实完全缺失且属必需
- 如果合同整体没有明显问题，findings 返回空数组 []
```

**最后那句"返回空数组"极其重要** —— 不写这句，模型会觉得"我得报点什么"，
于是在干净合同上也硬凑几条出来，误报率直接爆炸。

## 十、第八步：评测跑分 —— 唯一能证明"变好了"的东西

`backend/app/eval_runner.py`

### 三个必须支持的跑法

```python
run_eval(db, use_rules_only=True)                    # 规则引擎基线
run_eval(db, prompt_version=v1)                      # 指定 prompt 版本
run_eval(db, prompt_version=v2)
```

`use_rules_only=True` 不调模型，0 成本、0 延迟，可以用来：
- 做降级模式的基线对比
- 没网 / 没额度时演示

### 真实跑分结果（20 份合同 / 36 个埋雷 / 132 条正常条款）

| 跑次 | 配置 | 召回率 | 误报率 | F1 | 精确率 | 平均耗时 | token |
|---|---|---|---|---|---|---|---|
| #1 | 规则引擎基线 | 25.0% | 8.3% | 32.1% | 45.0% | 0ms | 0 |
| #2 | v1 初版 prompt | **88.9%** | **31.1%** | 58.7% | 43.8% | 6265ms | 14601 |
| #3 | v2 强化 prompt | 83.3% | **20.4%** | **64.5%** | **52.6%** | 5583ms | 22792 |

### 怎么读这张表

**规则引擎（#1）**：召回率只有 25%，也就是 36 个雷只抓到 9 个。
但误报率最低（8.3%）—— 因为正则只会命中它确定认识的东西，不乱猜。
它适合当兜底，不适合当主力。

**v1（#2）**：召回率 88.9%，36 个雷抓到 32 个，非常好。
但误报 41 条 —— 平均每份合同报 3 条不存在的问题。
法务一天看 20 份合同，就要多看 60 条噪音，很快就会弃用。

**v2（#3）**：召回率降到 83.3%（少抓 2 个），但误报从 41 条降到 27 条。
F1 从 58.7% → 64.5%，精确率从 43.8% → 52.6%。
**这是一次明确的正向优化**：用 5.6 个点的召回，换回 10.7 个点的精确度。

### 这个对比就是演示杀手锏

准备好这一屏：

> 同一份合同，同一批样本：
> - v1 漏 4 个雷、误报 41 条，F1 = 58.7%
> - v2 漏 5 个雷、误报 27 条，F1 = 64.5%
>
> 每次改 prompt 都跑一遍，分数变化一目了然。

**这比任何架构图都有说服力** —— 它证明你有可度量的闭环，而不是在讲故事。

### v1 那次的坑（真实教训）

第一次跑 v1 时，20 份合同**全部降级到规则引擎**，召回率显示 25%。
看起来像"v1 很差"，其实是 **v1 的 prompt 没要求 JSON 输出**，
模型返回自然语言，`extract_json()` 解析失败，于是走了降级。

这个分数根本反映不了模型的真实水平，对比毫无意义。
修法：给 v1 也加上最简的 JSON 格式要求（保留"粗糙"的其他方面）。

**教训**：评测结果异常时，先怀疑链路（降级？解析失败？），
再怀疑模型。否则你会基于假数据做决策。

## 十三、真实踩过的坑（按时间顺序）

这一节比前面所有理论都值钱 —— 全是实际调试出来的。

### 坑 1：`openai` 版本与 `httpx` 不兼容

**现象**：第一次端到端测试，27 项里 2 项失败，报错
`Client.__init__() got an unexpected keyword argument 'proxies'`

**根因**：`openai==1.39.0` 与 `httpx==0.28.1` 不兼容 ——
httpx 0.28 移除了 `proxies` 参数，而老版 openai 还在传它。

**修法**：`pip install --upgrade "openai>=1.60"`（实际装到 3.40.0）。
`requirements.txt` 里改成 `openai>=1.60` 并加注释说明原因。

**教训**：锁定版本要锁"下限 + 兼容性"，不要盲目 `==`。
依赖冲突的报错信息往往指向错误的地方（报 `Client.__init__`，实际是 httpx 的问题）。

### 坑 2：中文 category 没映射，评测指标全废

**现象**：评测召回率异常低，但看模型输出内容明明是对的。

**根因**：模型把 `category` 写成 `"违约责任"`，而 `VALID_CATEGORIES` 里只有 `"liability"`。
不匹配 → 归入 `other` → 评测时 `category` 匹配失败 → 判为没抓到。

**修法**：加 `CATEGORY_ALIASES` 映射表（30+ 条），在 `normalize_findings()` 里转换。

**教训**：**评测指标异常时，先查数据清洗层，再查模型。**
校验层的 bug 会伪装成"模型不行"。

### 坑 3：后端改了代码但没重启

**现象**：`clause_total` 字段前端一直读到 `undefined`，
财务权限提示永远不显示。API 返回的 JSON 里确实没有这个 key。

**根因**：`schemas.py` 里 `clause_total` 是 14:14:12 加进去的，
但后端进程是 14:09:35 启动的 —— **跑的是旧代码**。

**修法**：重启 uvicorn。

**教训**：改了后端代码没生效，第一件事查进程启动时间 vs 文件修改时间。

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like '*8210*' } |
  ForEach-Object { "PID=$($_.ProcessId) Start=$($_.CreationDate)" }
```

对比 `(Get-Item app/schemas.py).LastWriteTime`，一眼就能看出来。

### 坑 4：`required` 属性挡住了自定义校验

**现象**：Playwright 测试"空用户名提示"失败 —— 点了登录按钮，
期望看到「请输入用户名」，实际什么都没发生。

**根因**：`<input required>` 触发了浏览器原生表单校验，
表单的 submit 事件根本没被触发，`doLogin()` 里那句
`errEl.textContent = '请输入用户名'` 永远执行不到。

**修法**：`<form novalidate>` —— 保留 `required`（语义和无障碍需要），
但关掉浏览器原生校验，让 JS 自己管。

**教训**：原生校验和自定义校验会打架。要自定义提示，就得 `novalidate`。

### 坑 5：Windows 上 localhost 解析成 IPv6

（这个坑在之前的项目里踩过，这次直接规避了）

**现象**：前端请求挂 30 秒然后超时。

**根因**：Windows 上 `localhost` 同时解析到 `127.0.0.1` 和 `::1`，
浏览器优先走 IPv6，而 uvicorn 默认只监听 IPv4。

**修法**：所有地方统一用 `127.0.0.1`，不用 `localhost`。

### 坑 6：PowerShell 传中文 JSON 给 curl 会乱码

**现象**：`curl -d '{"username":"张三"}'` → 后端报 `JSON decode error`。

**根因**：PowerShell 对命令行里的中文做了编码转换。

**修法**：写 UTF-8 无 BOM 文件，用 `curl --data-binary "@file"`。
或者干脆用 Python 的 `urllib` + `ensure_ascii=False`。

### 坑 7：无 BOM 的 UTF-8 `.ps1` 在 PowerShell 5.1 里必错

（历史教训，这个项目没踩，但值得记）

含中文的 `.ps1` 如果存成无 BOM 的 UTF-8，
`powershell.exe` 5.1 会按 ANSI 解码 → 中文变乱码 → 解析器报 `Unexpected token` →
**脚本在第一个语句前就退出了**，既无报错弹窗也无日志。
表现为「运行了但没反应」。

**修法**：`.ps1` 要么纯 ASCII，要么带 UTF-8 BOM（`EF BB BF`）。

## 十五、如果要真上线，还差什么

这个项目是**教学用完整版**，不是生产系统。差距清单：

### 必须补（否则不能上线）

| 项 | 现状 | 生产要求 |
|---|---|---|
| 数据库 | SQLite | PostgreSQL（并发、备份、行级锁） |
| 密钥管理 | `.env` 明文 | KMS / Vault / 云密钥服务 |
| HTTPS | HTTP | 强制 TLS，HSTS |
| CORS | `allow_origins=["*"]` | 收窄到具体域名 |
| 限流 | 无 | 按 IP / 用户 / 租户三层限流 |
| 会话 | 8 小时 JWT 无刷新 | access + refresh 双 token，支持主动吊销 |
| 审计日志 | 同库、可被 DBA 改 | 独立存储 + 哈希链 / 写入 WORM 存储 |
| 文件存储 | 本地 `uploads/` | 对象存储 + 病毒扫描 |
| 密码策略 | 无 | 长度/复杂度/定期更换/登录失败锁定 |

### 应该补（影响体验和成本）

| 项 | 说明 |
|---|---|
| 异步任务 | 审查要 5–9 秒，应该走队列（Celery/RQ），前端轮询或 SSE |
| 可观测性 | OpenTelemetry + trace id，能查"这次请求为什么慢" |
| 缓存 | 同一份合同重复审查可以命中缓存 |
| 批量审查 | 一次上传 50 份，异步跑，出汇总报告 |
| 意见去重 | 同一问题多条意见合并 |
| 人工标注回流 | `reviewer_edits` 现在只存不加工，应该自动进训练集 |

### 架构上真正该改的一处

**现在 `Review` 表把 findings 存成一个大 JSON。**
生产环境应该拆成 `findings` 独立表，每条意见一行，带：
- `clause_id` 外键（而不是 `clause_no` 整数）
- `status`（pending / accepted / rejected）
- `reviewer_comment`
- `embedding`（做相似意见聚类）

这样才能做"这条意见历史上被采纳过几次"这类统计。
